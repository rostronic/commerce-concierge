# Phase 2a — Grounding the agent with RAG

*2026-09-17. What got built, why each decision went the way it did, and the four things
that only showed up by measuring.*

---

## 1. The problem RAG actually solves

Phase 1's tools answer from *structured* data: an order id maps to a record, a SKU maps
to a quantity. Policy questions are not like that. *"Can I return shoes I've worn once?"*
has no lookup key — the answer lives in a paragraph of prose, and the space of ways to
ask it is open.

You could try to put the whole policy corpus in the system prompt. For four short files
that even works. It stops working the moment the corpus is a real one, and it was never
the right shape anyway: you want the model reading *the two paragraphs that matter*, not
skimming forty. Retrieval-Augmented Generation is that idea and nothing more:

1. **Chunk** the corpus into passages that are each about one thing.
2. **Embed** each passage as a vector whose geometry encodes meaning.
3. **Retrieve** by embedding the question the same way and returning the nearest passages.

The architectural decision worth defending in an interview: **retrieval is a tool the
agent chooses to call**, not a step bolted in front of every request. `get_policy` is a
`@tool` exactly like `get_order_status`, so the model decides "this is about the rules"
versus "this is about a specific order." Pre-retrieving on every turn would fetch policy
passages for *"where is my order 10432?"* — wasted latency, and irrelevant text crowding
the context window. **Deciding which source of truth to consult is the agentic behaviour.**

## 2. What got built

| File | What's in it |
|---|---|
| `data/policies/*.md` | the corpus — returns, shipping, warranty, sizing |
| `data/inventory.json` | per-warehouse stock, backing `check_inventory` |
| `app/rag.py` | chunking, two embedding backends, the FAISS store, `search()` |
| `app/tools.py` | `+ get_policy`, `+ check_inventory` |
| `app/graph.py` | 4 tools bound; a system prompt that discriminates between them |
| `app/stub_model.py` | the offline reasoner learned **multi-hop** |
| `requirements-live.txt` | live extras split out, so the offline path needs no Google package |

**The thing to notice:** `graph.py`'s nodes, edges and state did not change, and the
Mermaid diagram in the README is the same picture as Phase 1. The loop was always
general. Growing from 2 tools to 4, and from single-shot to multi-hop, was a change to
*what the reasoner decides*, not to the machinery that carries the decision out. That is
the payoff for building the graph explicitly.

## 3. Four findings that only came from measuring

### 3.1 Hash collisions wreck ranking before anything else does

`HashingEmbeddings` hashes each word into one of *N* buckets. With `N=768` and 246
distinct terms in the corpus, 36 terms collided — and *"when will my refund show up?"*
retrieved **"Order processing"** as its top hit. The word `refund` was sharing a bucket
with an unrelated term.

```bash
.venv/bin/python -c "
from app.rag import load_policy_chunks, HashingEmbeddings, citation_for
chunks = load_policy_chunks(); texts = [c.page_content for c in chunks]
for dim in (768, 2048, 4096, 16384):
    e = HashingEmbeddings(dim=dim); dv = e.embed_documents(texts)
    buckets = [e._bucket(t) for t in e._idf]
    print(dim, 'colliding terms:', len(buckets) - len(set(buckets)))
"
```

| buckets | colliding terms | top-1 correct (8 questions) |
|---|---|---|
| 768 | 36 | 5/8 |
| 2048 | 13 | 6/8 |
| 4096 | 6 | 6/8 |
| **16384** | **2** | **7/8** |

**Lesson:** when a retriever ranks badly, inspect the *representation* before you start
rewriting prompts. The bug was two floors below where it showed up.

### 3.2 `faiss.IndexFlatL2` returns the **squared** distance

For unit vectors, `d² = 2 − 2·cos`, so the conversion is `cos = 1 − d²/2`. The trap is
that FAISS hands you `d²` already, so writing `1 - (distance ** 2) / 2` squares it twice.

What makes this dangerous is the failure mode: squaring is monotonic, so **the ranking
stays correct** and the output looks completely plausible. Only the *numbers* are wrong —
and the numbers are what Phase 3 will threshold on. Caught by hand-computing one cosine
and comparing:

```bash
.venv/bin/python -c "
from app.rag import _build_store, load_policy_chunks, citation_for, search
store = _build_store(); emb = store.embedding_function
chunks = load_policy_chunks(); dv = emb.embed_documents([c.page_content for c in chunks])
qv = emb.embed_query('when will my refund show up?')
print('manual :', max((sum(a*b for a,b in zip(qv,v)), citation_for(c)) for v,c in zip(dv,chunks)))
print('search():', [(round(s,4), citation_for(d)) for d,s in search('when will my refund show up?', k=1)])
"
```

**Lesson:** any derived number you never verify against a hand calculation is a number
you are trusting on vibes. Rankings can be right while scores are garbage.

### 3.3 A similarity threshold cannot decide answerability

The obvious way to make the agent refuse out-of-scope questions is "refuse when the top
score is low." It does not work here, and the measurement says so plainly:

| | min | max |
|---|---|---|
| 9 in-scope questions | **0.188** | 0.569 |
| 7 out-of-scope questions | 0.000 | **0.283** |

The ranges **overlap**, so no single threshold separates them. And the cause is
structural, not a tuning miss: cosine similarity normalises length away, so **short
chunks score high on almost anything**. Every out-of-scope question containing the word
"policy" — dog grooming, bicycle repair, renting tuxedos — retrieved the same three-line
`sizing.md > If the size is wrong` section at ~0.25.

This is why the demo deliberately keeps a **failing** query in it
(*"What's your policy on renting shoes for a wedding?"*). A demo that only shows the
happy path hides its own failure modes.

**Lesson:** a similarity score answers *"what is nearest?"*. A guardrail needs
*"does this passage answer the question?"*. Those are different predicates, and no amount
of threshold tuning converts one into the other.

### 3.4 Better embeddings fix ranking, not abstention

Swapping `HashingEmbeddings` for `gemini-embedding-001` (one line — `rag.configure(...)`)
fixed exactly the cases lexical matching cannot reach:

| question | hash embeddings | Gemini embeddings |
|---|---|---|
| "my sole came apart after a month" | returns / *Refund timing* ✗ | warranty / *What is not covered* ✓ |
| "how fast can I get them?" | 0.000, total miss ✗ | shipping / *Expedited shipping* ✓ |
| "are these true to size?" | sizing ✓ | sizing ✓ |
| **"can I pay in bitcoin?"** | shipping @ 0.268 ✗ | shipping @ **0.588** ✗ |

Real embeddings understand that *sole came apart* is a defect and *how fast* is about
shipping speed — no shared vocabulary required. But look at the last row: the
out-of-scope question scores **higher** under the better model, because modern embedding
models place all same-domain text close together.

**Lesson, and it's the one that matters:** retrieval quality and abstention are
independent problems. A bigger model buys you the first and not the second. That is the
entire argument for Phase 2b's grounding gate — it's a design consequence of a
measurement, not a checkbox from a tutorial.

### 3.5 (bonus) `AIMessage.content` is not always a string

Current Gemini models return a **list of content blocks** — typed dicts like
`{"type": "text", ...}` plus blocks carrying reasoning signatures — where older models
and our stub return a plain string. `print(msg.content)` is therefore correct offline and
dumps raw dicts with multi-kilobyte signature blobs the instant you pass `--live`. Fixed
with `_text()` in `app/cli.py`.

Same class of bug as the renamed classes in DESIGN.md §5: **code written against last
year's shape still runs, just wrongly.** And note it was only findable by running the
live path — the offline tests were all green.

Also learned the hard way in the same run: the free tier allows **20 requests/day** on
`gemini-3.8-flash`, and a full live demo exhausts it. Another reason the offline stub
path is not a toy — Phase 3's eval harness cannot run on a 20-request budget.

## 4. Smaller things worth keeping

- **Chunk on Markdown headings first.** `MarkdownHeaderTextSplitter` splits on the
  author's own semantic boundaries and lifts the headings into metadata — which is where
  the citations come from, for free. `RecursiveCharacterTextSplitter` then runs only as a
  size safety net. An answer nobody can verify is still a trust problem.
- **`hashlib`, not `hash()`.** Python salts `hash()` per process for strings, so an index
  built in one run would not match a query in the next. "Deterministic" has to mean
  across processes.
- **IDF is what makes lexical retrieval usable.** `return` appears in most of
  `returns.md` and discriminates nothing; `worn` appears once and pins the answer. Plain
  term frequency ranked *Exchanges* above the actual worn-returns rule.
- **A tool that fires with nothing to contribute is not harmless.** The stub classified
  "can I return these shoes?" as a policy question *and* a product question, stapling
  irrelevant catalog listings onto a correct policy answer. Extra calls are latency, cost,
  and noise in the model's context.
- **`already_run` is what makes the loop terminate.** Each tool fires at most once per
  user turn. LangGraph's `recursion_limit` would eventually stop a spinning agent, but
  running out of budget is not the same as knowing when you are done.
- **Pin the model id, never `-latest`.** An alias silently swaps the reasoner underneath
  the eval harness and makes any regression unattributable.

## 5. Your turn — exercises

These change working code, so you can always `git diff` to see what you did.

1. **Feel the collision bug.** Set `_HASH_DIM = 256` in `app/rag.py`, run
   `--demo`, and watch a policy answer go wrong. Put it back.
2. **Break the distance conversion.** Change `1.0 - distance / 2.0` back to
   `1.0 - distance ** 2 / 2.0` in `search()`. Note that the *citations stay correct* —
   that's the point of 3.2.
3. **Tune the chunker.** Set `_CHUNK_CHARS = 150` and re-run the separability measurement
   in 3.3. Prediction: smaller chunks make the overlap *worse*. Confirm or refute it.
4. **Add a tool.** Write `get_shipping_estimate(zip_code)` over seeded JSON. You should
   only need to touch `tools.py`, the `TOOLS` list, and the stub's router — `graph.py`'s
   nodes and edges shouldn't move at all. If they do, something is coupled that shouldn't be.
5. **Prep for the gate.** Write down, in one sentence, the exact question the gate node
   should ask the model. (Hint from 3.3: it takes *two* inputs, and "is this relevant?"
   is the wrong wording.)
